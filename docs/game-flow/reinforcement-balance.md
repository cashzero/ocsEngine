# 援軍比例與海運進攻平衡

## Scope

評估進攻方沒有 inland entry hex、只能經已持有港口接收地面援軍、SP 與 Repls 時，雙方的師級援軍比例、到達時間與港口吞吐量如何影響對局。這是設定的評估；New Game 已提供援軍設定（見 Current behavior），產品預設尚未更改。

## Current behavior

New Game 的 Order of battle 區有 Allied／Axis 各自的援軍比例下拉選單（0%、25%、50%、75%），選項顯示換算後的實際師數。比例四捨五入到整師，且最多延後總師數減一：至少保留一師開局在場。API 保留整數 0–100% 的輸入，預覽、排程驗證與部署使用同一個實際師數；例如六師的 API 100% 請求實際顯示與排程均為五師，一師的請求則為零師。無法在最早 T2 起排完、或沒有可延後師的正比例選項會停用並說明原因。

雙方共用首批到達回合（`NewGameRequest.reinforcements.firstTurn`）。被抽中的整師開局在援軍 Box，按編制順序均勻抽取，從首批回合起每回合到 1 師。最後一師至少有兩個 Game Turn 在場（首批回合 + 師數 − 1 ≤ 回合上限 − 1）。完成編輯（選擇選項或數字欄位失焦）後，才把首批回合壓低至可排程的值（不低於 T2）；仍排不下時，降低到可排程的最大已提供比例。清空或逐字編輯數字時不連帶改動其他援軍設定。不合法 API 請求由 `OPTIONS` 階段拒絕；不以迴圈逐一減少任意數值。

預設仍為無師級援軍、首批欄位 T4；攻方沒有 inland entry 時自動提高守方預設尚未實作。預覽顯示每方實際援軍師數與首批回合。海運方的援軍仍須經港口與 Sea Cap 上岸，排程只保證回合合法，不保證當回合一定上岸。既有卡車、飛機、獨立支援單位及容量不足時的待進場行為不屬於此比例。進攻方師數仍依 `ATTACKER_FORCE_RATIO = 2`；無 inland entry 不會自動減少或延後敵方主力。

港口生成與容量見 [Random map](../generator/random-map.md)，Sea Cap 預設見 [Deployment](deployment.md)，海運與供補規則的實作邊界見 [Rule coverage](../rule-engine/rule-coverage.md) 的 `movement.sea`。補給表收入大於卸貨量，只能證明 Box 可能累積 SP；它不是部隊每回合實際消耗量。維持 trace supply、燃料、戰鬥與失去補給線的情況必須分別觀察。

## Decisions

Allied 與 Axis 的比例分別設定；海運攻方所對應的守方自動預設仍待校準。下拉選單提供有限比例，避免任意數值與輸入中間態改寫設定。使用者確認保留排程必要時自動提前至 T2 的行為；此下限不代表海運進攻的建議平衡預設。T3／75% 或其他組合都是評估候選，沒有把樣本結果提升為已校準預設。

評估以完整師為單位，保留總 OOB、HQ、獨立部隊、守備隊、陣地與開局補給。整師比例不等於 counter 比例或全軍戰力比例；裝甲與步兵的編制、獨立支援與固定守備仍會影響實際戰力。不得單憑「守方 50% 援軍」推定場上只剩一半守軍。

不採用「港口容量 ÷ 補給表收入」直接作為守軍比例：收入不等於作戰需求，而且港口之外還有運補路徑、反擊切斷補給線、目標距離與部隊組成等因素。

## Assessment method

`scripts/sea-landing-balance.mjs` 固定每組種子的原始生成地圖、控制權、目標與 VP 門檻，只把指定完整師移到援軍 Box，指定 return turn 並使用合法進場。此方式隔離兵力時序，沒有重新部署剩餘部隊，因此不驗證未來部署演算法或 UI。

主要設定為 32×24 Western Europe、COMPACT、守方 6 師／攻方 9 師、2／3 個裝甲或機動師、八回合、10 月、flank sea、攻方 ports only、Sea Cap 5／0，雙方均使用現行 heuristic bot。每種設定使用四組完整種子，並分別測 Allied 與 Axis 進攻。

17 個候選設定包括：原配置；守方 25%、50%、75% × 首批 Turn 3、4、5；雙方 25%／25%、25%／50%、50%／50%（攻／守，Turn 4）；攻方港口改為 1 SP 或 4 SP；4 SP 港口搭配守方 50%／Turn 4；Sea Cap 1 搭配守方 50%／Turn 4。每方從首批回合起每回合到 1 師。

比例四捨五入到整師，按編制順序均勻抽取，保持完整編制。守方六師的 25%、50%、75% 實為 2、3、5 師；不等於精確的四分之一、二分之一、四分之三戰力。原編制先列裝甲／機動師，所以本次規則仍保留第一個裝甲師開局在場；未比較不同抽取方式。

容量敏感度測試把攻方開局持有的每個港口改為指定的 runtime printed capacity，保留 VP 與地形，藉此隔離吞吐量；不是把該港改生成城市。例如兩個港口各改為 4 SP，總港口容量是 8 SP，仍受 Sea Cap 5 的限制。海運方援軍仍須消耗港口與 Sea Cap，指定到達回合不等於當回合一定能上岸。排程超出第八回合的師保持在 Box，不以提前到達掩蓋。

### 設定的機械效果

六個守方師在八回合全部開局部署是 48 個「師×可參戰回合」。只計師數、不計戰力差別，分批延後的效果如下。這是排程算術，不是實測戰力或勝率。

| 名義援軍比例 | 實際延後／開局師數 | 首批 T3：守方師×回合 | 首批 T4 | 首批 T5 |
|---|---|---:|---:|---:|
| 0% | 0／6 | 48 | 48 | 48 |
| 25% | 2／4 | 43 | 41 | 39 |
| 50% | 3／3 | 39 | 36 | 33 |
| 75% | 5／1 | 28 | 23 | 18 |

75%／T5 的最後一師在 T9，超過八回合戰役，等同該師整場無法參戰。不能把這組解讀成純粹延後而沒有減少實際參戰兵力。HQ、獨立裝甲與反坦克、砲兵、固定守備的力量不包含在這張表。

`scripts/sea-landing-capacity-scan.mjs` 檢查固定預設種子的 48 組生成請求：18×12、32×24、64×48；守方 2、4、6、10 師；裝甲數 0 或 2；COMPACT 或 LARGE，Allied 攻、ports only、Sea Cap 5／0。全部可生成，攻方均只持有一個 2 SP 港口。三種尺寸都沒有隨兵力或 OOB 規模增加開局卸載量。

| 攻方／守方師數 | 攻方補給表平均收入 | 開局港口最大卸載量／Movement Phase | 卸載量／收入 |
|---|---:|---:|---:|
| 3／2 | 14.89T | 8T | 54% |
| 6／4 | 24.33T | 8T | 33% |
| 9／6 | 36T | 8T | 22% |
| 15／10 | 47.67T | 8T | 17% |

平均收入依 BTR 表全部 36 種雙骰結果計算；Supply Status 上限 12。數字只表示吞吐量與收入的差距，沒有假設每個師每回合必須吃 1 SP。這 48 組沒有實際對局；也未證明所有其他種子都只有一個 2 SP 港口。

各參數組使用相同四組 Map/OOB/deployment/rules 種子；不同動作與戰鬥會消耗不同骰序，不能視為每次擲骰完全相同。這是少量配對敏感度樣本，不是獨立確認試驗，也不代表人類玩家勝率。未涵蓋其他地圖風格、天氣、戰役長度與全套 OOB 規模的實戰。

## Assessment results

136 場八回合對局使用 `heuristic@66`，全部完成、零拒絕、零執行錯誤，逐動作合法重播的最終 state hash 全部一致。每格只有四組配對種子，表列「攻方勝場／4」，不把重複使用種子的 136 場當成 136 個獨立樣本。

| 守方名義援軍比例 | 首批回合 | Allied 進攻 | Axis 進攻 |
|---|---:|---:|---:|
| 0% | 無師級延後 | 1／4 | 1／4 |
| 25%（2 師） | 3 | 3／4 | 0／4 |
| 25%（2 師） | 4 | 2／4 | 0／4 |
| 25%（2 師） | 5 | 1／4 | 0／4 |
| 50%（3 師） | 3 | 1／4 | 1／4 |
| 50%（3 師） | 4 | 1／4 | 1／4 |
| 50%（3 師） | 5 | 0／4 | 1／4 |
| 75%（5 師） | 3 | 2／4 | 2／4 |
| 75%（5 師） | 4 | 2／4 | 3／4 |
| 75%（5 師） | 5 | 2／4 | 2／4 |

原配置兩方向均僅一局奪得過敵方目標。75%／T4 兩方向各三局奪得過目標；相對同種子原配置，攻方最終 VP 平均增加 Allied +3.25、Axis +7。攻方 attrition step 損失平均從 Allied 27.5、Axis 25.25 降至 15.5、2.75。它是本輪值得優先確認的候選，並非已確認的平衡預設：這個候選由同一輪多組比較選出，必須再以未見過的獨立種子驗證，不能用本輪勝率自行宣告成功。

50%／T4 在兩方向都沒有比原配置增加勝場；不能沿用評估前提出的「50% 應該足夠」假設。比例與到達時間沒有穩定的單調效果，且較少部隊開局也可能改善其供補負擔或改變 bot 的接敵與反擊選擇。此樣本不足以把這些現象各自確定為因果機制。

| 其他設定 | Allied 攻方勝場／4 | Axis 攻方勝場／4 | 解讀限制 |
|---|---:|---:|---|
| 攻／守各 25%，首批 T4 | 0／4 | 0／4 | 不能把雙方相同比例視為效果相抵 |
| 攻 25%／守 50%，首批 T4 | 1／4 | 1／4 | 沒有增加本樣本勝場 |
| 攻／守各 50%，首批 T4 | 1／4 | 1／4 | 攻方平均運入 SP 降至 28.5T／37T；上岸援軍競用容量 |
| 開局每港 1 SP，無師級延後 | 0／4 | 1／4 | 容量低但勝負仍受其他因素影響 |
| 開局每港 4 SP，無師級延後 | 1／4 | 1／4 | 平均運補提高到 115T／113T，但未增加勝場 |
| 開局每港 4 SP，守 50%／T4 | 2／4 | 0／4 | 不能假定加港口與延後守軍的效果可直接相加 |
| Sea Cap 1，守 50%／T4 | 0／4 | 2／4 | 低運量樣本仍可能勝利，不能從單組結果推定低 Sea Cap 較好 |

原配置平均運入 SP 為 Allied 54T、Axis 64T；75%／T4 為 81T、97T，部分來自奪港後增加可用容量。Box 仍平均累積 167T、154T，不能把該候選稱為解決吞吐量問題。

原配置開局可用港口容量依種子與方向不同：Allied 四組為 8、8、4、8T；Axis 為 16、8、8、8T。第一組 Axis 擁有兩個 2 SP 港口，Allied 只有一個。兩方向的兵種、目標距離與 VP 門檻也不同，因此不把方向差異全部歸因於港口。

以第一組 Allied 進攻為例，守方整師 50% 延後時，開局野戰 combat value 從 172.4 降至 115.2（約減 33%）；75% 延後時仍有 81.1（約保留 47%）。該指標不計固定守備、HQ 或卡車。50%／75% 的師並不等於移除相同比例的全軍力量。

### Bot 與測量限制

四局補給稽核（兩方向第一組的原配置與 50%／T4）沒有一般 MOVE／CHANGE_MODE 的 trace 中斷、feed 中斷或預覽不一致，也沒有被評為較差的撤退供補選擇。Allied 進攻原配置的耗損 trace 中斷由敵方行動觸發；50%／T4 另有敵方戰鬥觸發。這說明保護供補線也重要，不能將所有耗損解釋成港口 SP 不夠。

Axis 進攻原配置仍有一筆自身 `RESPOND_DECISION` 後的耗損、19 筆相位轉換與兩筆進場斷補記錄尚未逐一證明是否可避免；歸因記錄不是戰略意圖或錯誤的證明。沒有對全部 136 局完成完整補給或反事實策略稽核。這些限制使結果適合提出候選，不適合宣告 AI 或遊戲平衡驗收完成。

初始 snapshot 的 cached victory scores 為零，分析工具另依實際初始 hex control 與目標 VP 計算起始持有 VP；沒有把零分快取當作攻方初始 VP。原始 runner 的 `spentT` 只計 `SUPPLY_SPENT`，不含交易的 `RESOURCE_CONSUMED`，不是全部支出，本評估不使用它作總耗費結論。正式勝負使用遊戲結束的 victory 與既有 attack threshold。

研究中的 75%／T4 讓最後一師在八回合戰役的 T8 到達，不符合現行 UI 至少兩回合在場的限制，會被調整為 75%／T3。依目前選項，海運進攻較合理的下一輪候選是攻方 0%、守方 75%、首批 T3（本輪兩方向各 2／4 勝）；仍須獨立種子確認，不能直接宣告平衡。若保留 T4，六師中最多四師可延後；目前提供的比例中，50%（三師）可排入，75%（五師）不行。一般 inland-entry 進攻與 Meeting Engagement 的援軍預設未在本輪實戰校準。

## Known gaps

`sea-landing-balance`、`reinforcement-options`、`arrival-merged-selection` 的缺少行為、影響與關閉證據見 [TODO inventory](../quality/05-todo-inventory.md)。自動提高海運攻方所對應的守方預設仍未實作；選單與一局實際進場的驗證不等於完成平衡校準。

產品邊界依 [operation verification plan](../quality/03-product-operation-verification-plan.md)；本評估不提升 NG-11、MAP-08 或其他 UI 驗收列。後續實作須由 UI 設定明顯不同的 Map/OOB 與雙方援軍，預覽並開啟同一 package，完成整個 Game Turn 的合法行動、決策與交接，再走到所設定的首批回合實際進場；海運方須實際經港口上岸。截圖置於 `artifacts/` 並人工檢視。
