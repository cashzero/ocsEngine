# M9 對局紀錄研究與 heuristic@2

日期：2026-10-06。需求（使用者）：「我覺得用權重不太對 應該研究replay並改善策略」。
因此暫停權重訓練（[M10 訓練紀錄](M10-self-play-training.md)：4 代皆無顯著改善），改以重播對局找出輸的原因、修改策略、再以新 seed 驗證。

## 1. 工具

`scripts/ai-replay-study.mjs <ai-match 輸出目錄…>`：讀取每局最終存檔，以規則引擎逐步重播，統計每一方：

- 每個 objective 換手的時點、方式（移動經過、戰鬥後推進）、換手前是否有守軍、最近的守方戰鬥單位距離、奪取者是否停在格上；
- step 損失原因（斷補消耗、攻擊、防守、砲擊、超疊）與斷補消耗發生處離補給點、HQ、敵軍多遠；
- 每次被攻擊時守方的 stack 大小與相鄰友軍數；
- 斷補單位回合數、攻擊次數與戰果、整局未移動的單位。

輸出 `study.json` 與依「policy／勝負」分組的 `study.md`。`scripts/ai-match.mjs` 現在每局都存最終存檔（`--no-replay` 只略過重新載入）；
`--allied heuristic@<建置目錄>` 讓另一份建置（凍結的基準版本）在同一個 session 中對戰。

## 2. 發現（heuristic@1 互打 20 局，seed 11000–11019）

| 觀察 | 數據 | 結論 |
|---|---|---|
| 目標換手幾乎都發生在「空著」時 | 每方每局約 9–10 次空目標被拿走，有守軍時被拿走約 0.1 次 | 勝負取決於誰留下空目標 |
| 被拿走的空目標附近其實有兵 | 58% 在 3 格內有我方戰鬥單位，19% 就在隔壁 | 單位沒站在目標上，而不是兵力不足 |
| 奪下的目標多半沒人留下 | 55% 是路過奪取，沒有停在格上 | 下一回合就被翻回去 |
| 最大的 step 損失是斷補消耗 | 每方每局約 5.5 step（贏家也是） | 補給管理是勝負關鍵 |
| 斷補消耗的單位離補給很遠 | 59% 離最近補給點 > 10 格，66% 離 HQ > 6 格；84% 不在目標上 | 孤立的推進／獵殺部隊在餓死 |
| 斷補時有補給可吃卻分錯 | 例：28 個取用選項、只有 10T，先餵了砲兵與偵察，主力與 HQ 斷補 | 取用補給要依價值排序 |
| 「逐單位」補給範圍比「任何單位」小 | 多單位師須走全師共同路線（12.6f），引擎逐單位判定 | 移動評估要用逐單位範圍 |
| 被攻擊的多為落單單位 | 約一半的防守戰是單一單位、周圍沒有友軍，受攻擊時 95% 受損 | 試做「避免落單」扣分，但未改變此比例，已撤回 |

## 3. heuristic@2 的修改

| # | 修改 | 依據 |
|---|---|---|
| S1 | 奪目標要停在格上（且在補給範圍內，或最後兩回合）才給全額；路過只給 25% | 55% 路過奪取後被翻回 |
| S2 | 沒有守軍的己方目標，守備價值 ×1.5；唯一的守軍離開目標扣 30 × VP（目標在補給範圍內時） | 空目標換手 |
| S3 | 不在自己補給範圍內、3 格內也沒有補給的戰鬥單位，除最後兩回合外，以最近的補給範圍格為目標撤回 | 斷補消耗 |
| S4 | 移動評估使用逐單位補給範圍（`getTraceCoverage(seat, pieceId)`） | 12.6f 共同路線 |
| S5 | 補給階段依價值排序取用補給：HQ 優先，再依剩餘戰力 | 補給分配錯誤 |

中途曾讓停在敵後深處目標的單位因斷補被消耗（v2 對 v1 一度 9:12），加上 S1 的「需在補給範圍內」條件與 S5 後轉為領先。

## 6. 第三輪：主攻方向（heuristic@4，`bot-offensive-axis`）

## 7. 第四輪：拔除駐守單位與補給預算（heuristic@5，OOB 0.4.0）

OOB 0.4.0 互打時斷補單位回合從每方每局 2.1 增為 7.7。逐一檢查每個補給階段不在自己補給線上的戰鬥單位（`scripts/ai-oos-census.mjs`）：

| 不在補給線上的單位旁 3 格內 | v4 自己互打（20 局） |
|---|---|
| 只有敵方駐守單位 | 17% |
| 有敵方一般戰鬥單位 | 37% |
| 沒有敵軍 | 46% |

所以駐守單位的 ZOC 只是一部分原因；更多是電腦自己走出補給範圍，並以為「附近有補給堆或卡車就吃得到」——但 3 格內的同一堆補給被很多單位同時算進去。
兩項修改：

1. **拔除駐守單位**：我方單位 5 格內戰力 ≤ 2 的敵方堆疊列為攻擊目標（一個單位前往即可），攻擊它另有加分（它的 ZOC 切斷補給，價值高於它的 step 數）。
2. **補給預算**：不在補給線上但「吃得到補給」的判斷，改為 2 格內、且本步驟尚未分給其他單位的補給（每 2 RE 1T）。

### 驗收範圍與方法

實作前確定的步驟：完整對戰並保存重播；追查斷補前的自身與敵方行動；重現確認的缺陷；修正後重跑同一案例與新 seed 對戰；
檢查可避免的自身斷補是否消失及 VP 是否退步。Kill、Loss 以 step 計數，並另記消耗來源，不用 K/D 取代 VP。

基準為 `143f387b61657e59eb1830fd835c01e982af31fa` 的 heuristic@12。使用 generated Ground Duel，32×24、每方 6 師含 2 裝甲師、8 回合。
溫帶、東歐、地中海各 8 場自我對戰，修正後各重跑 8 場；再以新 seed 各跑 8 場新舊 bot 對戰，每組交換陣營。
自我對戰兩方 policy 相同，因此不使用會重複同局的 `--swap`。

| 地圖 | 基準與重跑 match index | 新舊對戰 match index |
|---|---|---|
| 溫帶 | 1210000–1210007 | 1211000–1211007 |
| 東歐 | 1210100–1210107 | 1211100–1211107 |
| 地中海 | 1210200–1210207 | 1211200–1211207 |

這裡列的是 `--start` 的 match index，實際 map／OOB／deployment／rules seed 由 runner 衍生，完整保存在 evidence。

新增 `scripts/ai-supply-study.mjs`：逐 action 重播，記錄每次 HQ 移動／切模式是否使友軍由有 trace 變成無 trace；
對每個消耗損失往前找最近一次失去 trace 的行動。**最近的斷補觸發者不等於唯一原因，也不證明戰術意圖或自身失誤**；

新工具亦檢查重播 final hash 和 step 損失總數；phase transition 與新登場即無 trace 的情形另列，不強制歸責。

### HQ 缺陷與修正

兩個真實存檔位置已固定為 regression fixtures：東歐 match 1210102 revision 97 的 HQ 切 Move mode，令 1 個友軍失去 trace；
地中海 match 1210206 revision 219 的 HQ 移動，令 7 個友軍失去 trace。修正前 policy 只評估 HQ 自己的目的地與前線距離，未檢查留在後方的依賴單位。

Rule explanation 現在提供僅屬於行動者的 HQ 調度補給影響，使用同一套地形、ZOC、HQ 與 formation trace 規則重算。
這是固定其他棋子的落點／模式查詢，不預測戰鬥、俘獲或敵人反應，也不消耗骰數。
Bot 先檢查切模式，再按原評分順序檢查 HQ 候選目的地；會中斷既有 trace 的選項被略過，dispatch 的備選也不放入未檢查的 HQ 移動。

### 本輪決策與驗證方法

heuristic@15 的一般移動與切模式，在既有 trace 檢查之外，加入己方無 trace 部隊的單位口糧檢查：
使用 Rule Engine 的 RE 成本、STRAT 禁止吃 SP、單一來源支付與現有戰鬥預留數量，比較行動前後的可支付口糧。
卡車的 cargo 仍按實際搬運關係定位，卡車不會在預判中取得沿途地格控制。一般運補及救援兩個卡車分支均套用檢查，
拒絕後會按原評分順序找安全的移動，也移除未檢查的 dispatcher 備選。HQ／戰鬥單位移動亦不能減少既有 SP 消費者的口糧能力。

撤退預判共用真正撤退的路徑、模式切換與 DG 規則，計入沿途確定的港口控制，
但不擲骰俘獲，也不提前執行後續戰鬥 queue。Bot 先減少必受損失，再比較不能取得單位口糧的數量、既有 trace 中斷數量，

## 12. 共用口糧庫存與支付順序（2026-10-13，IN PROGRESS）

本輪延續「先避免自行破壞補給」；驗收優先序維持 VP > Kill > Loss，不調整進攻評分。
實作前明列驗收：

1. 從 v15 完整對戰重播取得燃料、築壘、逐支餵兵及強制恢復內部存量的支付現場，記錄敵方斷補與己方支出的不同作用。
2. 共同分配必須遵守每個單位由單一可達來源支付、同來源群組 RE 合計後進位的真實規則；不能把一份庫存重複承諾給不同單位。
3. 可選支出前驗證既有可執行口糧承諾仍可支付；強制恢復優先於口糧，不能靠跳過必要行動或卡住流程保留庫存。
4. 用真實引擎執行群組支付、回放至下一個己方 Supply（含待決），核對實際庫存、餵養及消耗；不以查詢自己的數值作唯一證據。
5. 三地圖完整對戰、未使用 seed 交換陣營，記錄 VP、Kill、Loss、消耗、合法性與重播 hash；測試及 headless 結果不提升 UI operation 狀態。
